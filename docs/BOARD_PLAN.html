archwhere · board redesign

From inspector to workbench

The board shows you boxes because it was built to describe a map, not to work on one. Here is what is actually broken — including the alerting gap that no board design fixes — and a plan that turns six lenses into one surface where writing is the interface.

Diagnosis 01Runtime is empty for a one-line reason

RUNTIME_URL is not set, so /api/runtime returns {available:false, reason:"RUNTIME_URL not set"} and every component greys out. The board is behaving correctly; nothing is pointed at it.

Your obs app already serves the exact shape the board wants, on port 8900:

$ curl localhost:8900/api/arch-metrics
components: 11
  assistant-core  {"status":"warn","lines":["pm2 online","up 9 h","restarts 24522"]}
  pa-telegram     {"status":"warn","lines":["pm2 online","up 1 d","restarts 25"]}
  meetings        {"status":"ok",  "lines":["pm2 online","up 8 d","restarts 6"]}

So the Runtime lens lights up the moment you set it:

RUNTIME_URL=http://127.0.0.1:8900/api/arch-metrics npm run arch:mission

Two things that output is telling you unattended

24,522 restarts on assistant-core and pa-account, with 9 hours uptime. That is a crash loop, not a healthy service. statusFor() grades anything above 10 restarts as warn, so a service that has died twenty-four thousand times looks the same as one that restarted eleven times.

And outbox: {pending: 0, dead: 1, sent: 59} from /api/summary: one message is dead and nothing surfaces it.

Diagnosis 02It is liveness, not observability

This is the real answer to "Runtime does not show any observability". obs/arch-metrics.js derives status from one input — the pm2 process list:

function statusFor(proc) {
  if (proc.status !== 'online') return 'bad';
  if ((proc.restarts || 0) >= 10) return 'warn'; // flapping
  ...
}

Process up, process down, process flapping. That is all it knows. But the failure signals you want are already collected by the same obs app and served on /api/summary — they are simply never folded into the per-component view:

The data exists. The pipe into the map is one function wide.

Two things are missing from both sides, and they are the reason a failure count on its own cannot be read:

  • Traffic. 212 failures out of 300 requests is an outage. 212 out of two million is noise. Errors without a denominator are not a signal. The golden-signal set — latency, traffic, errors, saturation — exists precisely so a number can be interpreted; this board currently carries one of the four.
  • What changed. The highest-value fact in any incident is the last deploy. The board already holds PRs and git heat per component and never joins them to health, so the first question you ask when a card turns red is the one question it cannot answer.

Diagnosis 03Nothing pages you the real gap

A dashboard only works when somebody is looking at it. The crash loop above ran for nine hours and nobody knew, because no alert watches it.

What you have is obs/health-alert.js, and it is well built. Three consecutive red checks before it fires, one update per distinct reason, a six-hour reminder while red, a recovery message carrying the downtime, and nothing counted as alerted until the send actually succeeded. That is textbook flap suppression.

It watches one component out of eleven

The alerter consumes the Health app's own red/green endpoint and nothing else. No alert path references restarts, API failure rates or the dead outbox — grep the file and the only hit for restart is an unrelated log line.

You have a good alerting engine pointed at 9 % of your system. Widening it is cheaper than any board work in this document and worth more.

Diagnosis 04Six lenses make a viewer, not a workbench

Structure, Changes, Heat, Runtime, System flow, Record. Each is a different way of looking at the same map. None of them is a place where work happens, so every question costs a tab change and the answer never sits next to the thing you would do about it.

The attention rail is closer to right — {security, blocked, attention, mergeable} — but it is driven entirely by GitHub labels (rail.js reads security, blocked, needs-owner, owner-review). It cannot see a failing service, because runtime never reaches it.

DesignOne surface, three zones

Replace the lens tabs with a single working view. Nothing is hidden behind a tab; the two heavy drawings become drawers you pull open when you want them.

left · needs you

Attention

Failing services, blocked threads, PRs ready to merge, dead outbox items. One ranked list, severity-striped.

centre · the map

Components

One card per component: health dot, failure count, open PRs, open threads, last decision. Health and heat are a toggle on the card, not separate tabs.

right · the work

Thread

Write here. Mention an agent, read replies, see the PR it opened and the checks on it, without leaving the page.

Tab count goes from six to zero. System flow and Record become drawers — they are reference material, consulted rarely, and both are expensive to draw.

Writing is the interface

Today a comment becomes a GitHub issue labelled component:<id> with an appended mention. That is the right bus. What is missing is context: the agent receives your sentence and nothing else.

Linear's agent integration, generally available since July 2026, captures the entire issue description and comments as context when you mention an agent. Do the same, from the map — when you write @claude the no-answer rate is climbing on a component, the issue body should carry, automatically:

  • the component's declared file globs and dependencies, so the agent knows its boundary before it starts
  • its current runtime lines and recent failures — the agent reads the symptom you are reacting to
  • open PRs and the last decisions from the record, so it does not redo settled work
  • whether the component is a security zone, which should change how the agent behaves

That one change is the difference between a chat box and a brief.

The board gains a work state, with no second store

This is what the merged record makes possible. It already holds claim, work, review, signoff and decision entries, each attributed to an author, agent, model and vendor. Derive the columns from those entries plus GitHub — never from a new database:

ColumnDerived from
Proposedan open thread with no claim
Claimedclaim entry, unexpired, with its agent and role
In PRwork entry, plus the live PR and its checks
Reviewedreview entry — marked independent only when record independent passes
Signed offsignoff entry, verified Ed25519
MergedGitHub

Two properties fall out of this for free. Every card shows which agent and which model is holding it, because the record demands attribution. And a card cannot claim review by the same vendor that wrote the code, because record independent already refuses it.

PlanFive phases, each shippable alone

Phase 1 — Make failures visible, and make them page you start here

Nothing in this phase touches the board's layout, and it is the whole of your observability complaint. The last item in it is the most valuable thing in this document.

  • Set RUNTIME_URL. Runtime works today.
  • Widen the runtime contract so a number can be read: errors against traffic, the last deploy, and an honest unknown. 
    {"components": {"<id>": {
  "status": "ok|warn|bad|unknown",
  "deploy": {"at": "2026-11-05T14:02:00Z", "ref": "PR #221"},
  "signals": {
    "traffic":    {"value": 1840, "unit": "req/h"},
    "errors":     {"value": 212, "of": 1840},
    "latency":    {"p99_ms": 4800},
    "saturation": {"value": 1200, "unit": "queued"}
  },
  "failures": [{"name": "restarts", "count": 24522, "window": "9h",
                "severity": "bad"}],
  "lines": ["pm2 online", "up 9 h"],
  "links": [{"label": "errors", "url": "https://obs…/errors?c=<id>"}]
}}}
  • Errors always carry of. A count without a denominator is not a signal, and the board should refuse to render one as if it were.
  • unknown is not ok. A component whose signal is stale or absent must look different from a healthy one. Silence reading as green is how the nine hours happened.
  • Fold /api/summary into arch-metrics.js: per-component counts from voice.calls.{started,failed}, health.errorsLast10min, waRelay.refused/failed, outbox.dead — taking started as the denominator, not only failed.
  • Join the deploy. The board already knows merged PRs per component; put the last one on the card beside the health. "Red, and deployed 3 h ago" is a diagnosis. "Red" is a notification.
  • Grade on severity, not a single threshold. Restarts in the thousands is bad. Keep the rule in one function, make the numbers per-component config rather than constants, and test it.
  • Feed runtime into the attention rail so a failing component ranks beside a blocked thread.
  • Point the existing alerter at all of it. health-alert.js already has the noise rules right; give it arch-metrics as a second source so every component can page you, not just one. Do this first if you only do one thing.

Phase 2 — Collapse the lenses

  • One view: rail, map, thread. Health and heat become a per-card toggle.
  • System flow and Record become drawers, loaded on open as Mermaid already is.
  • Click a component anywhere and the thread opens beside it — never a navigation.

Phase 3 — Briefs instead of comments

  • Compose box with @agent autocomplete from the configured agent list.
  • Attach component context to the issue body automatically, as listed above.
  • Show agent replies inline with the PR it opened, its checks, and its declared model and vendor from the record.
  • Keep /api/merge as it is: the merge button acts with the human's token. Agents never merge.

Phase 4 — Work state on the board

  • Derive the six columns from the record and GitHub.
  • Show the holding agent and model on each card; show expiry on stale claims.
  • Mark the independence check on anything claiming review.

Phase 5 — Let the product take shape

The piece your note is really asking for: discussion that accumulates into a product rather than scrolling away.

  • Promote a thread to a decision. A button that writes a decision entry to the record, attributed, hash-linked, greppable months later. The conversation stays on GitHub; the conclusion becomes durable.
  • Specs on components. record spec put already versions a spec by content hash and supersedes the previous one. Surface the current spec on the card, so a component carries its intent, not only its globs.
  • A findings feed. finding entries from agents, on the component they concern — this is where "something is not working" gets written down by whoever noticed.

One thing to decide before Phase 1

The runtime contract is the seam between archwhere and whatever you run. Keep it deliberately dumb — status, lines, failures, links — so anyone can satisfy it from Prometheus, Datadog or a shell script, and archwhere never learns to speak a vendor's API. This is the same choice Backstage made and the reason its catalog outlived particular monitoring tools: the portal stays portable, and the adapter is the user's problem.

ScopeWhat this is not, and what it still lacks

Three things are deliberately out:

  • Not a metrics store. No time series, no retention. The board reads a current snapshot and links out for history.
  • Not a second source of truth. Threads stay GitHub issues, decisions stay record entries. If it is not in one of those, the board does not know it.
  • Not an agent runner. The bus stays GitHub; any agent that can read an issue can answer. That is what lets Claude, Kiro and anything else coexist.

And two are genuine shortfalls against normal operational practice, worth naming rather than hiding:

  • No SLOs, so every threshold is a judgement call. Proper practice derives alerting from an error budget and its burn rate, so you can tell "degraded but within budget" from "spending the quarter this afternoon". Per-component config is a step toward that, not a substitute. Revisit once there is enough traffic for a budget to mean anything.
  • No trend, by consequence of holding no history. A snapshot cannot answer "is this getting worse", which is usually the real question. The links field carries that weight; make sure it actually points somewhere with history rather than being decorative.

Related, and outside this plan: the raw material for deployment frequency, lead time, change failure rate and mean time to restore is all present in PRs, merges and failures, and none of it is computed. Less urgent than alerting, but it is the standard way to answer whether any of this is working.

BoundaryWhat stays free, and what the hosted plan sells

Decided now, before the first outside pull request, because the answer shapes where code is written rather than only how it is priced.

The principle

Free: anything one developer runs on one machine, for one repository. That is the whole CLI, check, the local board, the IR, SKILL.md, the GitHub Action, the MCP server and the local record.

Paid: anything that must keep running when nobody is at the keyboard, or that must be external to be worth trusting. Nothing is removed from the free tier to create the paid one.

That second clause is the test to apply whenever a feature is tempting to move behind the paywall. If it does not need to run unattended, and does not need to be a third party, it stays free.

Licence: keep MIT, and protect the name instead

Every human commit in this repository is the owner's, so relicensing is still possible — but that ends with the first outside contribution. Three things follow:

  • MIT stays. Hosting archwhere is trivial — zero dependencies, one Node process, 44 kB — so no licence makes operations a moat. The licence's job is adoption, and MIT is best at that. AGPL would deter resale at the cost of the enterprises that ban it outright, which is the wrong trade at this size.
  • The paid code lives in a private repository from its first commit. Then the core's licence has no bearing on revenue, and nothing has to be withdrawn later. Un-publishing a feature is far harder than never publishing it.
  • Trademark the name. A fork can take MIT code; it cannot be called archwhere. For Grafana, Redis and Elastic the mark, not the licence, turned out to be the asset.

Add a CONTRIBUTING.md carrying a DCO before merging anyone else's work, so the relicensing option survives.

Do not build the billing yet

The repository is six days old with five stars and one npm release, and the traffic from its launch day is already decaying. There is no demand signal to price against. Decide the boundary now so that no paid feature is accidentally published; build the free tier until something tells you what a team will pay for.
